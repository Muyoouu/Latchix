# ADR 0006: IDs and storage layout

- Status: Accepted
- Date: 2026-11-05
- Owners: Musa Yohanes
- Supersedes: none

## Context

Phase 0 must settle the default tenant and the on-disk layout before the first
schema is written. The blueprint requires opaque tenant and root storage keys,
non-reused IDs, and no caller-supplied host paths. Leaving these choices open
would leak into the schema, API, backup format, and test fixtures.

SQLite `INTEGER PRIMARY KEY` can reuse the row ID of a deleted tenant. A reused
ID would misattribute retained audit rows and break external references. A
tenant or root name in a filesystem path invites rename, collision, and path
injection bugs.

## Decision

1. Entity IDs for tenants, roots, users, groups, SSH keys, grants, API keys,
   sessions, idempotency keys, and share links are UUIDv7 values stored as
   lowercase canonical text.
2. Audit event IDs use `INTEGER PRIMARY KEY AUTOINCREMENT`. Audit order is
   monotonic and audit IDs are never reused.
3. IDs are generated by the server or by a migration. The API does not accept a
   caller-supplied ID on create.
4. The default tenant is seeded with `slug = "default"`. Its ID is generated
   during the first migration. Tests resolve it by slug, not by a hard-coded ID.
5. The `default` slug is reserved. The default tenant may be renamed or
   disabled, but it is not hard-deleted.
6. A default root named `default` is seeded for the default tenant and enabled.
   Users require a live `home_root_id`, so the seed must provide one.
7. Tenant and root `storage_key` values are 128-bit random lowercase hex
   strings, 32 characters long. They are not derived from a slug, name, or
   username. Tenant and root keys are generated separately and unique.
8. The on-disk layout is:

   ```text
   <storage.root>/tenants/<tenant_storage_key>/roots/<root_storage_key>/
   ```

9. `storage.root` comes from configuration and must be an absolute local
   directory. The server opens it once and treats it as the storage boundary.
   Tenant and root paths are resolved from the database, never from an API
   request body or query string.
10. The service user owns the storage tree. New tenant and root directories are
    created with mode `0700`. Files and directories inside a root inherit the
    process umask and the SFTP create mode policy.
11. Tenant and root storage keys are immutable for the life of the row. Moving
    a tenant to a different key is a separate migration with a copy and
    verification step, not a rename.
12. The database and storage tree are one backup unit. A backup that restores
    only one of them is invalid.

## Consequences

- Text UUID indexes are larger than integer indexes. At single-host v0.1 scale,
  the simplicity and non-reuse guarantee are worth the bytes. Revisit a BLOB
  representation only after a benchmark shows a real problem.
- UUIDv7 is time-ordered but not strictly monotonic inside one millisecond.
  Never use an entity ID for audit ordering. Use the audit event integer.
- Storage keys are not human-readable. Operators need the database to map a key
  to a tenant or root. A future `doctor` or admin view can provide that map.
- Default tenant tests must look up by slug. A hard-coded UUID would make the
  seed brittle.
- A tenant rename does not move data. A tenant storage migration is a separate
  lifecycle operation.
- Tenant deletion is soft. Storage garbage collection needs an explicit,
  audited job after the retention window.

## Alternatives considered

- Integer `AUTOINCREMENT` for every entity. Rejected. It leaks counts, makes
  import and embedding harder, and a reused ID can misattribute retained data.
- UUIDv4 for every entity. Rejected. Random indexes have poor locality and no
  time ordering.
- BLOB UUIDs. Deferred. They are compact but make debugging, SQL inspection, and
  API conversion harder. Revisit only with evidence.
- Slug, username, or group name in a path. Rejected. Renames, case folding, and
  path injection make this unsafe.
- A fixed UUID for the default tenant. Rejected. The seed should generate an ID
  so a restored or imported database cannot collide with a reserved value.

## Evidence

- Earlier SQLite tests showed `INTEGER PRIMARY KEY` reused a deleted tenant ID.
  UUID text keys avoid that class of misattribution.
- `openat2` containment tests showed that path traversal and symlinks must be
  blocked at the descriptor boundary, not by string prefix checks.
- Phase 2 migration tests must verify that IDs are never reused, that the
  default tenant and root are seeded exactly once, and that storage keys stay
  unique.

## Open items

- Default tenant rename policy in the API and UI.
- The benchmark threshold that would justify BLOB UUIDs.
